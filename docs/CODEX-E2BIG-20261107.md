## Síntoma

En una conversación con imágenes de Seedream v5.5 Edit, tras una imagen cualquier mensaje posterior, incluso «?», falla con `Codex: spawn E2BIG`.

## Dónde se inicia Codex y qué falla

Nexus no lanza Codex: habla por HTTP con el puente de AXEL (`:8788` en el S25, dentro de Termux; el ASUS solo reenvía bytes con un relé TCP). El puente es `/root/axel-native-v2/bridge/server.ts`, **fuera de este repo** (copia de referencia: `egodivergente/axel-native`, `bridge/server.ts`). Su rama `codex` hace:

```ts
const codexArgs = ["exec", "--dangerously-bypass-approvals-and-sandbox", "--skip-git-repo-check", …, "-o", tmpOutput, multiTurnPrompt];
const child = spawn("/usr/local/bin/codex", codexArgs, { stdio: ["ignore", "pipe", "pipe"] });
```

`multiTurnPrompt` = todos los mensajes que no son `system` unidos como «Usuario: … / Asistente: …» (los `system` se descartan) más un manifiesto de capacidades. Va como **un único argumento** y `stdin` está en `ignore`. Linux limita cada argumento a 128 KiB (`MAX_ARG_STRLEN` = 131 072 B); `spawn` devuelve `E2BIG` al superarlo.

### Mediciones en el puente real (solo tamaños; peticiones «responde OK» con conversaciones de diagnóstico propias)

| Petición | Resultado |
|---|---|
| `prompt` de 100 033 B / 120 033 B / 130 033 B / 130 993 B | completa |
| `prompt` de 132 033 B / 140 033 B | **`spawn E2BIG`** al instante (0,3 s) |
| un único mensaje de 140 KB (el último va en `prompt`) | completa |
| historial (sin `system`) de 120 000 B en 6 mensajes | completa |
| historial de 139 200 B / 144 000 B / 160 KB / 275 KB | **`spawn E2BIG`** |
| un mensaje de usuario de 130 033 B / 165 033 B (más un `system` aparte) | completa / **`spawn E2BIG`** |

El umbral queda en 131 072 B por cadena, el del kernel. Con el `server.ts` real y un `codex` simulado el fallo se reproduce igual sin parche y desaparece al pasar el texto por stdin.

### Por qué en tu chat y por qué «?» también falla

En la copia del repo el puente descarta el `system` (no he podido leer la copia parcheada del móvil; las mediciones en vivo son coherentes con ello), así que Nexus lo envía **dentro del primer mensaje de usuario** (54 158 B: prompt de sistema y esquemas de las 33 herramientas). Eso deja unos 77 KB de los 128 KiB para toda la conversación. Medido con el orquestador real (contenido sintético, formato exacto de Nexus):

| Conversación | Texto que el puente pasa a la CLI |
|---|---|
| «?» en un chat nuevo | ≈ 56 KB |
| 1 turno de imagen (cargas de skills + generación) + «?» | ≈ 105 KB |
| 3 turnos de imagen + «?» | ≈ 131,5 KB → **E2BIG** |
| 8 turnos de imagen + «?» | ≈ 182 KB → **E2BIG** |

Un mensaje corto no cambia nada: el historial viaja entero en cada turno, así que una vez superado el umbral **todos** los mensajes siguientes fallan, también «?», y reintentar no ayuda (es determinista).

## No es el formato ni la resolución de la imagen

- Las imágenes **no viajan** al puente: `renderMessage` solo escribe `[Imagen adjunta (png, N bytes)]`. No encontré ninguna herramienta que meta base64 en sus resultados (revisado `agent-core` y `app/assistant`).
- El fallo se reproduce con **cero imágenes** y texto de relleno.
- Lo que crece es el texto del historial (resultados de skills, esquemas, respuestas). Si además Seedream v5.5 Edit devuelve una imagen con otro formato o resolución, es un problema distinto que **no se ha investigado aquí** (no hay datos de ese resultado).

## Corrección

1. **Puente** (`tools/bridge-patches/codex-stdin/apply.mjs`): usa la interfaz real de la CLI. `codex exec --help` (v0.167.0): «PROMPT: si no se da como argumento (o si se usa `-`), las instrucciones se leen de stdin». El parche cambia el último argumento por `"-"`, abre `stdin` como pipe y escribe el texto con `child.stdin.end(multiTurnPrompt)` (con manejador de `EPIPE`). Tres líneas, sin tocar nada más. Es estricto: si el fichero no tiene exactamente la forma esperada (un `codexArgs` con `multiTurnPrompt` al final y un único `spawn`) no modifica nada y sale con código 2. Admite la copia desplegada (con `-c model_reasoning_effort`, `env`, otro nombre de variable). Hace copia de seguridad (`server.ts.bak-codex-stdin-<fecha>`), conserva permisos y es idempotente. No hay archivos temporales con el texto, así que no hay nada que proteger ni limpiar.
2. **App** (`AntigravityProvider`): si el puente responde E2BIG, el error ya no es «spawn E2BIG» a secas: indica el tamaño medido del texto (solo bytes), el límite de 128 KiB, que no es la imagen y qué hacer. Si el texto enviado es pequeño (<100 KB) no culpa al historial. **No recorta el historial ni quita imágenes.**

No se hizo, a propósito: recortar o resumir el historial para esquivar el límite (ocultaría el problema), tocar la rama `grok` del puente (usa `--single <texto>` con el mismo defecto; no se verificó que esa CLI lea de stdin, así que no se inventa) y sincronizar `desktop/agent/core` (está desactualizada desde antes de vc176; el script de sincronización cambia ~2 000 líneas ajenas).
